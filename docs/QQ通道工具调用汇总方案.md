# QQ 通道按模型请求汇总工具调用

**状态：待验收。** 建议只在 `src/channels/qq.py` 实现。QQ 已经能看到一次模型响应请求的全部函数，也能收到每个函数带 `call_id` 的结果。让 QQ 记住这一次有哪些调用，最后一个结果到齐时发一条私聊消息，即可沿用现有的工具执行和会话记录流程。

## 用户在 QQ 里会看到什么

假设用户问“看一下 README，再告诉我现在的时间”。模型第一次响应同时请求两个工具，第二次响应给出答案。QQ 应依次收到两条消息。第一条在两个工具都有结果后发送，示意如下。

```text
请求调用 read_file，args={"path":"README.md"}，返回结果预览：执行成功，# miniAgent
请求调用 get_current_time，args={}，返回结果预览：执行成功，2026-11-21T10:3…
```

第二条是助手回答。如果模型在给出答案前又请求了一批工具，QQ 会在两者之间多收到一条该批的摘要。直接回答的问题只发助手回答。这里的“一次”指主对话循环中一次成功返回的 `responses.create()`；同一个 QQ 用户问题可能经过多次这样的调用。

## 现有代码已经提供了什么

| 位置 | 实际行为 | 本方案如何使用 |
| --- | --- | --- |
| `src/message_process/turn_runner.py` · `TurnRunner.run_turn()` | 先把整个 `response.output` 一次交给 `persist_and_dispatch_items()`，再筛出所有 `function_call` 并等待 `execute_batch()` 返回，之后才发下一次模型请求。 | 同一响应里的工具声明天然属于同一批。 |
| `src/tools/tool_manager.py` · `execute_batch()` | 并发提交任务，按模型声明顺序等待和处理结果。单个工具抛出的普通异常也会转换成错误结果。每项结果有原调用的 `call_id`。 | 以 `call_id` 匹配，即使同一工具被调用两遍也能对上各自的参数。 |
| `src/common/common.py` · `persist_and_dispatch_items()`，`src/tools/tool.py` · `ToolResult.log_output()` | 完整结果先落盘。实时分发给通道的 `function_call_output.output` 已替换为预览字符串，含成功或失败、图片数量和最多 50 字的正文。 | QQ 可以直接缩短实时预览。读取会话文件或解析图片都会增加无用工作。 |
| `src/channels/qq.py` · `QQChannel.send()`、`QQReply` | `replies[request_id]` 已保存私聊对象、原消息 ID、被动回复序号和助手文本。普通 `items` 只收集助手文本，`done` 合并发送并释放请求状态。审批和错误单独即时发送。 | 本批工具信息与现有回复共用生命周期。 |

在当前同步分发顺序下，收到最后一个结果时，每个工具都已结束，下一次模型请求也尚未发起。此时就可以发送摘要。另加一个 `PostToolBatch` 事件会让所有通道都收到新的协议消息，而 QQ 手上已经具备判断条件。

## 建议的实现

**1. 在 `QQReply` 上保存当前模型响应的工具行。** 建议用一个有序列表，每行只存配对用的 ID、工具名、用于展示的参数、可空的结果预览。函数的结果初始为 `None`，表示还在等待。批次通常很小，收到结果时按 `call_id` 在列表中找到对应行即可。列表顺序就是最终展示顺序。运行中每个 `request_id` 都有自己的 `QQReply`，同一请求的连续批次依次复用这个列表。

**2. 在 `QQChannel.send()` 的 `items` 分支里，先处理完这次事件的所有条目，再检查一次是否发摘要。**

| 条目 | 处理 |
| --- | --- |
| `message`，角色为 `assistant` | 继续收集 `output_text` 或 `refusal` 到 `reply.texts`，交给 `done` 发送。 |
| `function_call` | 按顺序追加一行，从 `name`、`arguments`、`call_id` 取值。内置工具与 MCP 工具都走这一分支。 |
| `function_call_output` | 按 `call_id` 填入结果预览。参数错误、审批被拒和执行异常各自占一行，都算该调用完成。 |
| `web_search_call` | 当前配置启用了托管搜索。它随模型响应返回，无后续本地结果事件。按原位置追加已完成行，工具名用 `web_search`，参数取 `action` 中实际返回的操作和查询参数，预览使用条目提供的状态或结果信息。只有状态时就写“状态 completed”等实际状态，连结果信息和状态都没有时写“未提供结果详情”。 |

仅当列表非空且每一行都有结果预览时，才拼成一条文本。先取出文本并清空本批，再等待 QQ 发送。这样即使发送失败，后续的模型响应也可以建立自己的批次。先遍历完整个事件尤其重要：同一响应可能先列一个已完成的托管搜索，再列两个等待执行的函数，此时三行应一起发。仅含托管搜索和助手回答时，可以当场发搜索摘要，随后由 `done` 发回答。

**3. 在 QQ 侧固定展示格式。** 每个调用一行，各行用换行分隔。工具参数取自模型传入的原始值，合法 JSON 紧凑化并保留中文。对格式错误的参数保留原文预览，工具返回的错误行仍能解释发生了什么。建议参数先按 **120 字符** 截断，避免 `write_file` 的正文占满私聊消息。这是拟议的展示值。

结果取**现有预览的前 20 个字符**，状态和图片数量计入长度，超长时另加一个 `…`。例如，纯图片结果可显示“执行成功，返回 2 张图片”，空结果显示“执行成功”。按这个口径，20 个字符里能看到的正文会随状态前缀长度变化。若产品希望保证展示 *20 个正文字符*，就需要在工具结果仍有结构时分别传正文、状态和图片数量。当前方案直接复用预览，QQ 无需反向拆解中文日志。

**4. 把工具摘要作为 QQ 单聊主动文本发送。** 这是本方案最需要确认的取舍。官方规则将同一条单聊原消息的被动回复限定为 **4 次**。假设已有一次审批、三次工具摘要，最终回答就会成为第 5 次发送。光递增 `msg_seq` 解决的是去重，无法增加次数。[QQ 消息收发规则](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/overview.html)

建议在 `qq.py` 增加专门发送工具摘要的小方法，目标仍取当前 `reply.target`。本地已安装的 SDK 支持调用 `post_c2c_message(openid=reply.target, msg_type=0, content=text)`，省略被动回复的 `msg_id`，也无需递增 `reply.seq`。审批、错误和最终回答继续通过现有 `_send_text()` 关联原消息。主动消息受用户接收开关和平台频控影响，实际可达性需在验收时用目标 QQ 账号验证。如果希望只用被动回复，则要接受长任务中减少独立摘要条数，例如给审批和最终回答留出次数，将溢出的摘要随最终回答合并。这会改变多轮时的发送时机。[QQ 单聊发送接口](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_users_user_openid_messages.post.html) · [主动消息接收与频控](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/overview.html)

## 失败与中断

- **工具失败。** 失败预览来自同一个结果事件。该行和本批成功的行一起发，方便对照哪些调用拿到了结果。
- **工具等待审批。** `request_approval` 仍需立即送达，用户回复 `yes` 或 `no` 后工具才能产生结果。审批输入有独立的 `request_id`，其 `done` 只清理审批输入对应的回复对象。
- **整轮中断。** 若 `done` 到达时列表还有等待中的调用，随 `QQReply` 释放这些行。已完成批次已经发送，半批不伪装成完整摘要。恢复会话时，历史内容通过其他事件读取，也不会重新推送旧摘要。
- **摘要发送失败。** 复用现有 `MessageDispatcher.send()` 的异常处理，SDK 返回空结果则按现有 QQ 发送方法抛出发送异常。记录请求 ID、批内调用数和失败原因即可。工具执行和最终回答继续，不自动重发，以免请求超时但 QQ 实际已收到时出现重复。若遇到整条消息过长，验收时单独记录实际限制；逐工具拆成多条会破坏本需求的发送粒度。

## 文件范围与验收

业务代码预计只涉及 `src/channels/qq.py`：扩展 `QQReply`，补充每行数据的表示与预览格式化，在 `QQChannel.send()` 收集和判定完成，并加入摘要发送方法。会话 JSONL 和模型下一轮输入继续使用原始工具结果。展示摘要只存在于当前 QQ 请求和私聊里。无需增加依赖、配置项或数据库字段。

| 验收场景 | 预期 QQ 表现 |
| --- | --- |
| 模型直接回答 | 只收到一条助手回答。 |
| 同一响应两次调用 `read_file`，参数不同，第二个先执行完 | 第一个结果事件到达时无摘要。两项到齐后收到一条两行消息，文件名、结果与声明顺序对应。 |
| 一次问答跨四批函数调用，再给出答案 | 主动消息可达时，依次收到四条独立摘要和一条最终回答；工具摘要不占原消息的被动回复序号。 |
| 同一批包含成功、审批拒绝或异常、纯图片结果 | 审批提示先到。本批完成后仅发一条摘要，包含成功信息、失败原因预览、图片数量。 |
| 仅有托管搜索，或搜索与本地函数出现在同一响应中 | 前者直接发一条搜索摘要。后者等本地结果齐全后合发，搜索状态与本地结果各占一行。 |
| 参数过长、结果正文超长或有换行 | 每次调用仍占一行，按约定截断，完整原始输入与工具结果可在会话记录中核对。 |
| 两个请求交错、某批中断或主动消息被拒 | 每条摘要只含所属请求的工具，发给对应用户。中断时丢弃未完成批次。主动消息被拒时有发送失败日志，最终回答仍走被动回复。 |

# 多通道设计

> 状态：常驻端、独立终端、单消费者与 Agent 事件流已实现；QQ 已实现好友私聊适配，并通过真实鉴权、网关 READY 与心跳验证。QQ 真实消息收发尚未联调；配置热更新和执行池仍为后续扩展。

## 1. 目标与范围

一个用户使用同一套 Agent，通过终端、QQ、后续网页等不同入口对话。模型、工具和长期记忆由常驻程序统一管理，不做用户或通道之间的记忆隔离。

- 常驻程序独立运行；终端作为客户端另外启动，通过 WebSocket 连接。
- 多个入口可以选择同一个会话，共享历史；同一会话一次只执行一轮请求。
- 输入通过队列调度，输出通过 Dispatcher 和通道注册表发送，不随请求传递回复函数。
- 第一版使用单消费者，保留后续扩展执行池的边界。
- 终端通道与 QQ 好友私聊已接入公共队列；暂不处理 QQ 群聊、频道、图片或语音。

## 2. 整体结构与职责

```text
终端客户端：TerminalUI                 QQ / 后续其他平台
        ↕ WebSocket                         ↕ 平台协议
TerminalChannel                         QQChannel
        └──────────── put ──────────────────┘
                       ↓
                 有容量限制的输入队列
                       ↓ consume
                  Runtime 协调层
         输入校验、命令识别、会话管理、锁、执行调度
                       ↕
           agent_loop(messages, ...)
              模型请求、工具执行、上下文压缩
                       ↓ yield 事件
              Runtime.process_event()
           持久化 → 运行日志 → Dispatcher
                                  ↓
               通道注册表[channel_id].send(reply_target, event)
                                  ↓
                             对应客户端
```

| 模块 | 职责 |
| --- | --- |
| 通道基类与子类 | 定义生命周期和发送接口；子类实现协议连接、输入转换、输出发送与资源清理。 |
| 通道管理器 | 读取配置，根据类型创建通道实例，启动、注册和停止实例。 |
| 输入队列与消费者 | 缓冲输入、限制积压，按调度规则交给执行入口。 |
| Runtime | 校验输入、处理命令、管理会话和锁，消费 Agent 事件并组织持久化与分发。 |
| SessionStore | 保留现有 JSONL 序列化、追加、加载和中断恢复职责。 |
| Dispatcher | 根据 channel_id 查找实例，调用其 send(reply_target, event)。 |
| agent_loop | 维护本轮模型上下文，调用模型和工具，通过异步生成器产出事件。 |
| 终端客户端 | 读取键盘输入、显示菜单和历史、渲染事件，不直接访问模型或会话文件。 |

Runtime 作为协调入口，内部保持会话管理、事件处理和执行调度的职责边界，避免把所有逻辑堆入一个函数。

## 3. 输入与输出约定

### 3.1 统一输入 InboundMessage

| 字段 | 含义 |
| --- | --- |
| request_id | 本次请求标识，用于关联输出和日志。 |
| channel_id | 通道实例标识，例如 terminal_main、qq_main，不是通道类型名。 |
| reply_target | 该实例内部的回复目标，由通道解释；终端使用具体连接标识，QQ 使用具体聊天目标。 |
| session_id | 本次请求所属的 Agent 会话标识。 |
| input | 输入文本，既可为普通问题，也可为 /new、/resume 等命令。 |

不再单独设置 kind、payload 或 connection_id。Runtime 统一识别 input 中的命令；普通输入才转换为模型用户消息。

通道接收输入时绑定并校验来源信息，不能直接信任客户端声明的 channel_id 或 reply_target。请求入队前固定 session_id，后续切换会话不改变已入队请求的归属。

channel_id 与 reply_target 共同确定返回地址：一个终端通道可以监听多个客户端连接，因此只使用 channel_id 不足以定位回复目标。

### 3.2 Agent 事件与分发

Agent 产出业务事件，Runtime 为输出补充 request_id、session_id、channel_id、reply_target 等关联信息。Agent 不负责选择通道或维护连接。当前 items 事件保存原始消息项和可选 model_name；permission 事件由外层回填 allowed，再恢复生成器。

| 事件内容 | 处理方式 |
| --- | --- |
| 原始模型输出、工具结果、系统续跑消息 | 先写入会话 JSONL，再发送展示事件。 |
| 排队、执行完成、错误等状态 | 记录相应日志并分发，不作为模型消息写入 JSONL。 |
| 权限审批请求 | 分发给本次请求的入口，等待明确答复。 |

持久化保留原始消息项与工具 call_id，不用终端展示文本替代原始记录。通道可以按需选择展示内容，例如终端展示工具过程，QQ 仅发送最终回答和必要提示。

Dispatcher 通过实例注册表查找通道；传输失败记录 request_id、session_id、channel_id 和目标信息，不能冒充发送成功。

## 4. 请求执行与事件时序

### 4.1 单消费者流程

1. 通道收到输入，完成协议解析，构造 InboundMessage 并放入有容量限制的队列。
2. 消费者取出请求，Runtime 校验内容、识别命令并解析目标会话。
3. 普通对话取得会话锁，处理上次中断遗留的工具调用，开启 turn 并持久化用户输入。
4. Runtime 使用 async for 消费 agent_loop 产出的事件，统一执行持久化、日志和分发。
5. 本轮正常结束后，由外层安排长期记忆提取，保留后台任务并在常驻程序退出时统一收尾。
6. 正常结束、异常和取消都通过 finally 释放锁；消费者完成该队列项的确认后继续处理下一项。

第一版所有 Agent 请求由同一个消费者串行执行。队列控制积压和消费顺序；后续需要限制请求频率时，在调度处增加限速，队列本身不等于限速器。

排队仅保存在内存中。已入队但尚未开始的请求不等于已经写入会话，第一版不承诺常驻程序重启后恢复排队请求。

### 4.2 yield 与持久化

agent_loop 改为异步生成器，移除对 TerminalUI 和 SessionStore 的直接调用。yield 表示产出一个事件并暂停，不表示本轮结束，也不等于模型逐 Token 流式响应。

```text
模型返回原始响应
  → yield 整批模型输出
  → Runtime 按顺序逐项持久化，再分发
  → 继续迭代生成器，Agent 更新上下文并执行工具
  → yield 工具结果
  → Runtime 持久化结果，再分发
  → 继续下一次模型请求
```

一次响应包含多个工具调用时，先记录整批响应，再执行其中任何工具。工具调用和结果沿用原始 call_id，保留现有中断恢复语义。

持久化失败必须停止本轮并关闭生成器，不能继续执行尚未记录的工具调用。展示或网络发送失败与持久化失败分别处理：回复失败不应使已接受的 Agent 任务中断。

上下文压缩仍由 Agent 负责。本次只迁移现有记录职责，不把压缩后完整恢复列为已完成能力；相关限制继续遵循 [持久化设计](持久化设计.md) 和 [记忆压缩设计](记忆压缩设计.md)。

## 5. 会话、命令与断线

### 5.1 会话与历史

常驻端统一持有会话历史、存储对象和会话锁。各入口维护当前选中的 session_id；多个入口可以选择相同会话，长期记忆共用。客户端首次连接使用内部 /attach 命令取得默认会话与历史快照。

- 同一会话的输入、上下文修改、工具循环和消息持久化受同一把锁保护。
- 新建、恢复和删除会话由常驻端处理，避免客户端直接修改会话文件。
- 客户端连接或切换会话时，常驻端发送历史快照；实时输出默认回复本次请求来源。
- 第一版通过重新打开或刷新获取其他入口产生的历史，暂不实现跨入口实时广播。
- 同一把锁覆盖所有执行入口；未来增加消费者后，同一会话仍需按输入顺序串行处理。

### 5.2 终端命令

| 输入 | 目标行为 |
| --- | --- |
| 普通文字 | 入队执行一轮对话。 |
| /new | 常驻端准备新会话并返回标识，终端切换到该会话；首次对话输入时才创建 JSONL。 |
| /resume | 从常驻端获取会话列表，本地菜单选择后请求恢复并获取历史。 |
| /delete | 从常驻端获取列表，本地二次确认后请求删除；常驻端检查执行状态再操作。 |
| /q | 退出终端客户端，保持常驻程序运行。 |

客户端完成菜单选择后，将具体会话标识作为命令参数发回。命令不写入模型上下文，不增加 turn_id；命令失败保留当前会话。正在执行或仍有排队请求的会话不得直接删除。

### 5.3 断线与权限审批

终端随时可连接和断开。断线后，常驻端清理连接资源；已接受的对话请求继续执行和落盘，旧 reply_target 的输出不自动转发给另一个连接。重新连接后通过历史快照恢复展示。

权限审批不能继续使用常驻端的 input()。Agent 产生审批请求后，外层通过通道发送，按审批标识等待答复；无可用连接、连接断开或审批超时，明确拒绝并记录原因。

审批答复仍可使用 input 中的专门命令表达，但必须在进入普通对话队列之前识别，直接交给等待中的审批项。否则唯一消费者等待审批，而审批又在等待该消费者，会形成死锁。

## 6. 通道生命周期与配置

### 6.1 基类和注册表

通道基类约定 start()、send(reply_target, event)、stop() 三个异步操作，实例创建时取得 channel_id 和输入队列。基类不限定主动连接还是被动监听。

- TerminalChannel：在常驻端监听本地 WebSocket，管理连接与消息收发；TerminalUI 留在客户端。
- QQChannel：主动连接 QQ 官方网关；获取访问令牌和机器人资料，再查询网关，收到 READY 才作为已就绪实例注册。READY 后按 Hello 指定间隔发送心跳并检查 ACK。
- 后续网页优先复用已有 WebSocket 消息协议，有独立行为时再增加通道子类。

使用两个注册表区分类型和运行实例：

| 注册表 | 映射关系 |
| --- | --- |
| 类型注册表 | 通道类型 → 通道类或创建方法。 |
| 实例注册表 | channel_id → 已启动的通道对象，供 Dispatcher 查找。 |

### 6.2 启动与配置变化

启动顺序：读取并校验通道配置 → 初始化共享运行资源 → 创建通道实例和消费者 → 启动监听并注册可用实例。终端监听默认绑定本机地址。

配置使用稳定的实例 ID，包含 type、enabled 和通道连接参数。一个 QQ 实例增加到三个 QQ 实例，只增加实例配置，不修改 Runtime。

当前通过 .channels.yaml 在启动时读取配置，ChannelManager 提供 add、remove、start、stop，Dispatcher 持有已就绪实例；尚未监听配置变化。后续配置热更新通过比较新旧配置实现：新增实例启动、删除实例停止接收并完成已有请求后关闭、参数变化更新或重启对应实例；非法配置保留旧实例并记录原因。现有 remove 是关闭资源的基础接口，后续热更新还需补上待处理请求的排空策略。

新通道类型需要先提供对应实现并注册；仅新增类型名称不会自动实现协议。运行中动态加载新类和已加载代码的热替换，不属于第一版范围。

### 6.3 QQ 好友私聊适配

- 使用 qq-botpy 1.x 的 Token、BotHttp 和 BotAPI 完成鉴权及 REST 调用；不直接运行 SDK 的 Client.run。SDK 的 Client.close 不负责完整取消网关和心跳任务，因此使用项目已有的 websockets 16.x 管理连接及任务生命周期。
- `.channels.yaml` 的 QQ options 配置 app_id_env、secret_env、is_sandbox；环境变量名默认 QQ_APP_ID、QQ_APP_SECRET，凭据放在已被 Git 忽略的本地 `.env`。好友私聊默认使用正式 API。
- 订阅 public_messages 对应的事件位，但只处理 C2C_MESSAGE_CREATE。reply_target 使用用户 openid；request_id 关联原始 QQ msg_id，发送时附带 msg_id 和递增 msg_seq，使用被动回复接口。
- 私聊 input 直接进入公共队列；session_id 留空，执行时跟随 Runtime 的共享当前会话。因此 `/new` 或 `/resume <会话ID>` 后，后续 QQ 输入跟随新的共享当前会话；已绑定会话的终端仍保留自己的会话选择。
- 助手文本缓存到 done 后合并回复，不回显用户输入、不逐条发送工具调用与结果。会话提示、错误和审批及时发送；`/resume` 返回会话列表，通过完整 ID 恢复，不使用终端菜单。
- `/approve <审批ID> allow|deny` 在入队前交给 ApprovalBroker；普通队列积压或消费者等待时仍能处理审批答复。通道停止会拒绝该通道尚在等待的审批。
- 初次连接失败或超时直接报告启动失败；首次 READY 后断线每隔 3 秒重新获取网关并鉴权。stop 取消并等待网关、心跳，清理本轮回复关联并关闭 HTTP 客户端。

本版只支持单分片机器人和纯文本。超长文本切分、富媒体、断线消息补偿与完整去重暂不处理。真实收发仍需用户在 QQ 客户端配合验证；连接成功不代表实际收发权限和内容审核已验证。

## 7. 执行池扩展与本轮实施边界

### 7.1 保留执行调度边界

消费者只负责取出请求并调用统一执行入口，Agent 执行通过独立的 Runner 边界提供事件流。通道、输入结构和 Dispatcher 不依赖消费者数量，也不直接依赖线程池或进程池。

后续可以把单消费者的执行方式替换为多个执行任务、线程池或进程池，选择依据是阻塞 I/O、CPU 工作和隔离需求。无论使用哪种方式，都需满足：

- 同一会话顺序执行；不同会话的计划和可变执行状态独立，长期记忆仍按本项目约定共享。
- 会话调度、JSONL 写入和输出分发保留明确的唯一管理方，工作单元只提交执行事件。
- 进程间传递可序列化的请求与事件，不直接传递 WebSocket 连接、异步锁、模型客户端或 MCP 会话。
- 工作者跨线程或进程运行时，其异步客户端和连接由对应运行环境创建、关闭；普通进程内异步队列不能直接当作跨进程通道使用。
- 跨执行边界仍需保证工具调用先落盘再执行，必要时由协调端确认持久化成功后才让工作者继续。

当前同步阻塞的工具操作需要避免长期占用常驻事件循环；可以在执行边界逐步迁出，不能仅增加消费者数量就认为监听和收发已经不会阻塞。

### 7.2 已落地的文件边界

| 文件 | 实现内容 |
| --- | --- |
| src/server.py、src/__main__.py | 常驻启动、共享资源与通道的初始化和关闭。 |
| src/terminal.py、src/ui/terminal_ui.py | 独立客户端、键盘输入、菜单、事件和历史展示。 |
| src/channels/base.py、manager.py | InboundMessage、通道基类、Dispatcher、配置与实例管理。 |
| src/channels/terminal.py、qq.py | 终端 WebSocket 收发、QQ 官方鉴权与好友私聊适配。 |
| src/runtime/runtime.py、runner.py、permissions.py | 队列消费、会话状态、锁、事件持久化、执行边界和审批。 |
| src/agent/core.py | 异步事件生成器，不依赖终端或 SessionStore。 |

## 8. 运行与验证

启动常驻端：python -m src；另开终端：python -m src.terminal。WebSocket 使用 websockets 16.x，默认地址为 ws://127.0.0.1:8765。QQ 启用后由同一常驻进程连接，网关断线可重新连接；终端客户端自动重连、配置热更新、线程池和进程池均未实现。

本次用户明确要求编写并执行测试，覆盖如下：

- tests/unit/test_channels.py：真实 WebSocket 与本地 SDK 模拟响应，覆盖新建、工具批次先落盘、审批允许和拒绝、历史共享、删除、断线继续执行、服务重建恢复、持久化失败阻止工具执行。
- tests/unit/test_sessions.py：原有 JSONL、call_id、工具和恢复校验，已适配异步事件消费。
- tests/unit/test_qq.py：本地真实 WebSocket 模拟 QQ 网关，覆盖 Hello/Identify/READY/ACK、首个心跳携带 READY 序号、忽略群消息、私聊入队与原始 msg_id 回复、审批绕过满队列、`/new` 到 JSONL 的往返、初次失败和超时清理。
- tests/integration/live_qq.py：读取本地 QQ 配置，经正式 ChannelManager 完成真实令牌获取、机器人资料查询、网关 READY 和心跳 ACK，停止后检查没有新增后台任务。2026-11-15 已通过；没有调用模型或发送真实 QQ 消息。调试发现 READY 前发送心跳无法收到 ACK，已改为 READY 后启动心跳。当前本地回归共 18 项通过。
- tests/integration/live_channels.py：独立常驻进程与终端客户端，使用实际 prompt-toolkit 输入框及菜单投喂按键，完成 /new、分两轮真实调用 read_file 与 PowerShell、断开重连、/resume 和历史续聊；5 次主模型请求。测试不替代人工确认终端排版与按键手感。
- 原有 live_sessions.py、live_mcp.py、live_mcp_http.py 已适配新的 Agent 事件入口，分别验证真实跨进程历史恢复、stdio MCP 和 HTTP MCP 调用。

测试仅使用 tests 下独立临时目录；关闭本次创建的连接、后台任务和子进程后，无论成败均清理配置、日志、会话和工具文件，不删除正式会话或记忆。依赖变更仍只修改 pyproject.toml，由用户执行 uv lock、uv sync。

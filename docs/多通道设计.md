## 1. 基本说明

暂时默认就一个用户，都用同一套 Agent(长期记忆，会话历史等都是共用)，支持通过终端、QQ、后续网页等不同(通道)入口进行对话。

- 常驻程序独立运行；终端作为客户端另外启动，通过 WebSocket 连接。
- Runtime 将 submit 回调交给 ChannelManager，再传入各通道；通道解析输入后直接调用 submit()，输出通过 MessageDispatcher 和通道注册表发送，不随请求传递回复函数。
- Runtime 管理异步请求任务，max_concurrent_requests 限制最多同时处理 10 个请求；不同会话可并行，同一会话由锁串行。
- 终端通道与 QQ 好友私聊持有 submit 回调，直接提交输入和断线通知，不持有 Runtime 对象；暂不处理 QQ 群聊、频道、图片或语音。

## 3. 输入与输出约定

### 3.1 统一输入 InboundMessage

| 字段 | 含义 |
| --- | --- |
| request_id | 本次请求标识，用于关联输出和日志。 |
| channel_id | 通道实例标识，例如 terminal_main、qq_main，不是通道类型名。 |
| reply_target | 该实例内部的回复目标，由通道解释；终端使用具体连接标识，QQ 使用具体聊天目标。 |
| session_id | 本次请求所属的 Agent 会话标识。 |
| input | 输入文本，既可为普通问题，也可为 /new、/resume 等命令。 |

不再单独设置 kind、payload 或 connection_id。AgentRuntime 统一识别 input 中的命令；普通输入才转换为模型用户消息。

通道接收输入时绑定并校验来源信息，不能直接信任客户端声明的 channel_id 或 reply_target。submit 接受请求时固定 session_id，后续切换会话不改变已接受请求的归属。

channel_id 与 reply_target 共同确定返回地址：一个终端通道可以监听多个客户端连接，因此只使用 channel_id 不足以定位回复目标。

### 3.2 Agent 事件与分发

Agent 产出业务事件，AgentRuntime 为输出补充 request_id、session_id、channel_id、reply_target 等关联信息。Agent 不负责选择通道或维护连接。当前 items 事件保存原始消息项和可选 model_name；permission 事件由外层回填 allowed，再恢复生成器。

| 事件内容 | 处理方式 |
| --- | --- |
| 原始模型输出、工具结果、系统续跑消息 | 先写入会话 JSONL，再发送展示事件。 |
| 等待、执行完成、错误等状态 | 记录相应日志并分发，不作为模型消息写入 JSONL。 |
| 权限审批请求 | 分发给本次请求的入口，等待明确答复。 |

持久化保留原始消息项与工具 call_id，不用终端展示文本替代原始记录。通道可以按需选择展示内容，例如终端展示工具过程，QQ 仅发送最终回答和必要提示。

MessageDispatcher 通过实例注册表查找通道；传输失败记录 request_id、session_id、channel_id 和目标信息，不能冒充发送成功。

## 4. 请求执行与事件时序

### 4.1 直接提交与并发控制

1. 通道完成协议解析，构造 InboundMessage，直接调用注入的 submit 回调，继续接收协议消息。
2. submit 是同步函数，固定目标会话并创建 Runtime 管理的异步请求任务后立即返回，通道不等待本轮执行完成；任务通过 Semaphore 后识别命令或直接执行对话处理函数。
3. 普通对话取得会话锁，处理上次中断遗留的工具调用，开启 turn 并持久化用户输入。
4. AgentRuntime 使用 async for 消费 agent_loop 产出的事件，统一执行持久化、日志和分发。
5. 本轮正常结束后，由外层安排长期记忆提取，保留后台任务并在常驻程序退出时统一收尾。
6. 正常结束、异常和取消均释放锁与并发名额，发送 done；任务结束后从 Runtime 请求表移除。

不设置通道输入队列、合并输入流或公共 Agent 执行队列。通道通过 submit 直接提交，执行调度由 Runtime.submit 和 Semaphore 负责。max_concurrent_requests 在 config.yaml 配置，当前为 10；达到上限后已接受的任务异步等待名额，不阻塞通道接收。该上限限制同时处理的请求数，不限制每秒请求数或等待任务数量。同一会话等待锁的请求也占用名额。审批答复和断线通知由 submit 直接处理，不占名额。

等待和执行中的任务仅保存在内存；尚未开启 turn 的请求不等于已经写入会话，暂不承诺重启后恢复等待请求。

### 4.2 yield 与持久化

agent_loop 改为异步生成器，移除对 TerminalUI 和 SessionStore 的直接调用。yield 表示产出一个事件并暂停，不表示本轮结束，也不等于模型逐 Token 流式响应。

```text
模型返回原始响应
  → yield 整批模型输出
  → AgentRuntime 按顺序逐项持久化，再分发
  → 继续迭代生成器，Agent 更新上下文并执行工具
  → yield 工具结果
  → AgentRuntime 持久化结果，再分发
  → 继续下一次模型请求
```

一次响应包含多个工具调用时，先记录整批响应，再执行其中任何工具。工具调用和结果沿用原始 call_id，保留现有中断恢复语义。

持久化失败必须停止本轮并关闭生成器，不能继续执行尚未记录的工具调用。展示或网络发送失败与持久化失败分别处理：回复失败不应使已接受的 Agent 任务中断。

上下文压缩仍由 Agent 负责。本次只迁移现有记录职责，不把压缩后完整恢复列为已完成能力；相关限制继续遵循 [持久化设计](持久化设计.md) 和 [记忆压缩设计](记忆压缩设计.md)。

## 5. 会话、命令与断线

### 5.1 会话与历史

常驻端统一持有会话历史、存储对象和会话锁。各入口维护当前选中的 session_id；多个入口可以选择相同会话，长期记忆共用。客户端首次连接使用内部 /attach 命令取得默认会话与历史快照。

- 同一会话的输入、上下文修改、工具循环和消息持久化受同一把锁保护。
- 新建、恢复和删除会话由常驻端处理，避免客户端直接修改会话文件。
- 客户端连接或切换会话时，常驻端发送历史快照；实时输出默认回复本次请求来源。
- 第一版通过重新打开或刷新获取其他入口产生的历史，暂不实现跨入口实时广播。
- 同一把锁覆盖所有执行入口；并发提交时，同一会话仍按锁的获取顺序串行处理。

### 5.2 终端命令

| 输入 | 目标行为 |
| --- | --- |
| 普通文字 | 提交执行一轮对话。 |
| /new | 常驻端准备新会话并返回标识，终端切换到该会话；首次对话输入时才创建 JSONL。 |
| /resume | 从常驻端获取会话列表，本地菜单选择后请求恢复并获取历史。 |
| /delete | 从常驻端获取列表，本地二次确认后请求删除；常驻端检查执行状态再操作。 |
| /q | 退出终端客户端，保持常驻程序运行。 |

客户端完成菜单选择后，将具体会话标识作为命令参数发回。命令不写入模型上下文，不增加 turn_id；命令失败保留当前会话。正在执行或仍有排队请求的会话不得直接删除。

### 5.3 断线与权限审批

终端随时可连接和断开。断线后，常驻端清理连接资源；已接受的对话请求继续执行和落盘，旧 reply_target 的输出不自动转发给另一个连接。重新连接后通过历史快照恢复展示。

权限审批不能继续使用常驻端的 input()。Agent 产生审批请求后，外层通过通道发送，按审批标识等待答复；无可用连接、连接断开或审批超时，明确拒绝并记录原因。

审批答复仍可使用 input 中的专门命令表达，但由 submit 在获取并发名额之前识别，直接交给等待中的审批项，避免全部名额等待审批时答复无法执行。

## 6. 通道生命周期与配置

### 6.1 基类和注册表

通道基类约定 start()、send(reply_target, event)、stop()。start() 成功返回 True，可跳过的连接失败返回 False；实例接收 channel_id、submit 回调与自身协议配置，直接提交 InboundMessage 和 ChannelDisconnected，不持有 Runtime 或审批对象。Submit 类型约定回调为同步函数，返回请求任务或 None。基类不限定主动连接还是被动监听。

- TerminalChannel：在常驻端监听本地 WebSocket，管理连接与消息收发；TerminalUI 留在客户端。
- QQChannel：主动连接 QQ 官方网关；获取访问令牌和机器人资料，再查询网关，收到 READY 才视为启动成功。READY 后按 Hello 指定间隔发送心跳并检查 ACK。
- 后续网页优先复用已有 WebSocket 消息协议，有独立行为时再增加通道子类。

使用两个注册表区分类型和运行实例：

| 注册表 | 映射关系 |
| --- | --- |
| 类型注册表 | 通道类型 → 通道类或创建方法。 |
| 实例注册表 | channel_id → 通道对象，启动前注册以支持即时回复，启动失败时移除，供 MessageDispatcher 查找。 |

### 6.2 启动与配置变化

启动顺序：读取并校验配置 → AgentRuntime 创建共享资源及恢复会话 → 等待 MCPManager 启动完成 → 启动 ChannelManager。通道收到输入即可直接提交，此时 MCP 工具已就绪，无需输入缓冲或额外就绪事件。ChannelManager 在调用通道 start 前先注册实例，避免启动期间收到输入后无法回复；start 返回 False、抛出异常或被取消时移除注册。终端监听默认绑定本机地址；监听端口被占用等 OSError 在 TerminalChannel 中记录日志并继续抛出，由入口结束程序并清理资源。

配置使用稳定的实例 ID，包含 type、enabled 和通道连接参数。一个 QQ 实例增加到三个 QQ 实例，只增加实例配置，不修改 AgentRuntime。

当前由 Config.load() 一次读取 config.yaml，AgentRuntime 内部创建 ChannelManager(config, message_dispatcher, self.submit)，两者共享同一个 Config 和 MessageDispatcher 实例；管理器从 config.channels 取得实例配置，提供 add、remove、start、stop，并将 submit 原样传给各通道，MessageDispatcher 持有通道实例；尚未监听配置变化。后续配置热更新通过比较新旧配置实现：新增实例启动、删除实例停止接收并完成已有请求后关闭、参数变化更新或重启对应实例；非法配置保留旧实例并记录原因。现有 remove 是关闭资源的基础接口，后续热更新还需补上待处理请求的排空策略。

新通道类型需要先提供对应实现并注册；仅新增类型名称不会自动实现协议。运行中动态加载新类和已加载代码的热替换，不属于第一版范围。

### 6.3 QQ 好友私聊适配

- 使用 qq-botpy 1.x 的 Token、BotHttp 和 BotAPI 完成鉴权及 REST 调用；不直接运行 SDK 的 Client.run。SDK 的 Client.close 不负责完整取消网关和心跳任务，因此使用项目已有的 websockets 16.x 管理连接及任务生命周期。
- `config.yaml` 的 QQ options 配置 app_id_env、secret_env、is_sandbox；环境变量名默认 QQ_APP_ID、QQ_APP_SECRET，凭据放在已被 Git 忽略的本地 `.env`，由 Config 解析后传给 QQChannel，通道不再自行读取环境变量。好友私聊默认使用正式 API。
- 订阅 public_messages 对应的事件位，但只处理 C2C_MESSAGE_CREATE。reply_target 使用用户 openid；request_id 关联原始 QQ msg_id，发送时附带 msg_id 和递增 msg_seq，使用被动回复接口。
- 私聊 input 通过注入的 submit 回调直接提交；session_id 留空，提交时跟随 AgentRuntime 的共享当前会话。因此 `/new` 或 `/resume <会话ID>` 后，后续 QQ 输入跟随新的共享当前会话；已绑定会话的终端仍保留自己的会话选择。
- 助手文本缓存到 done 后合并回复，不回显用户输入、不逐条发送工具调用与结果。会话提示、错误和审批及时发送；`/resume` 返回会话列表，通过完整 ID 恢复，不使用终端菜单。
- `/approve <审批ID> allow|deny` 由 submit 直接交给 ApprovalBroker；并发名额用尽时仍能处理审批答复。通道停止时通过 submit 提交 ChannelDisconnected，由 Runtime 调用 ApprovalBroker.disconnect 拒绝该来源尚在等待的审批。
- 初次连接失败或超时在 QQChannel 中记录日志、关闭连接并返回 False，ChannelManager 移除该实例的注册，不中断常驻程序；首次 READY 后断线每隔 3 秒重新获取网关并鉴权。stop 取消并等待网关、心跳，清理本轮回复关联并关闭 HTTP 客户端。

本版只支持单分片机器人和纯文本。超长文本切分、富媒体、断线消息补偿与完整去重暂不处理。真实收发仍需用户在 QQ 客户端配合验证；连接成功不代表实际收发权限和内容审核已验证。

## 7. 执行池扩展与本轮实施边界

### 7.1 保留执行调度边界

submit 创建的请求任务进入处理函数后，AgentRuntime 直接调用 agent_loop 并消费事件流，不再设置 Runner/AgentRunner 抽象层。执行池暂不实现，未来有具体需求再引入执行边界。通道、输入结构和 MessageDispatcher 不依赖调度实现，也不直接依赖线程池或进程池。

后续可以在 submit 及 Runtime 内部替换调度实现，接入线程池或进程池，选择依据是阻塞 I/O、CPU 工作和隔离需求。无论使用哪种方式，都需满足：

- 同一会话顺序执行；不同会话的计划和可变执行状态独立，长期记忆仍按本项目约定共享。
- 会话调度、JSONL 写入和输出分发保留明确的唯一管理方，工作单元只提交执行事件。
- 进程间传递可序列化的请求与事件，不直接传递 WebSocket 连接、异步锁、模型客户端或 MCP 会话。
- 工作者跨线程或进程运行时，其异步客户端和连接由对应运行环境创建、关闭；普通进程内异步队列不能直接当作跨进程通道使用。
- 跨执行边界仍需保证工具调用先落盘再执行，必要时由协调端确认持久化成功后才让工作者继续。

当前同步阻塞的工具操作需要避免长期占用常驻事件循环；可以在执行边界逐步迁出，不能仅增加协程并发数就认为监听和收发已经不会阻塞。

## 9. 集中配置与启动依赖

```python
config = Config.load()                 # config.yaml 与 .env，只在配置层读取。
runtime = AgentRuntime(config)        # 构造 client、MCPManager 和 ChannelManager；此时不连接网络。
await runtime.start()                 # 内部启动 MCP、恢复会话并启动 ChannelManager。
# 退出时 await runtime.stop()，统一关闭通道、请求任务和共享资源。
```

模型名称、base_url、最大并发请求数 max_concurrent_requests、PowerShell 超时、工作区、额外允许目录，以及通道和 MCP 服务器由 YAML 配置。会话、技能、记忆、日志、工具结果和历史归档的目录名常量分别放在各自负责的模块，仅保存相对名称，使用时与 src/config.py 的 PROJECT_ROOT 拼接，不从 YAML 读取。密钥继续使用环境变量，不写入 YAML。工作区和额外允许目录的相对路径以所选配置文件所在目录为基准，默认工作区为项目根目录。

AgentRuntime 直接消费 agent_loop 的事件，并安排辅助记忆提取。__init__ 统一构造 AsyncOpenAI、MCPManager 和 ChannelManager，并向管理器传入 self.submit；start 恢复会话后，依次等待 self.mcp.start() 与 self.channels.start()，不额外捕获或包装启动异常。通道直接提交输入，无需输入读取任务或额外就绪事件；agent_loop 直接使用 MCPManager 的工具列表，不接收 tools_ready 或其他初始化任务。Runtime 不设置 accepting 开关；退出时关闭通道并等待已有请求和记忆任务，最后关闭 MCP 和模型客户端。

原 src/server.py 已合并到 src/__main__.py；src/runtime/runner.py、.channels.yaml 和 .mcp.json 已移除，没有保留兼容入口。文件工具、权限检查、系统提示词、记忆及上下文压缩显式使用当前 Config，不再依赖各模块的全局工作区、模型名或目录实例。算法阈值和协议常量仍留在对应实现模块。

本轮 submit 并发与 Runtime 生命周期重构仅做静态检查，相关测试代码已同步，未运行测试或真实连接验证。

当前输入依赖方向：AgentRuntime → ChannelManager(config, message_dispatcher, self.submit) → Channel。通道持有提交回调，解析完成后直接调用 self.submit(message)，断线时调用 self.submit(ChannelDisconnected(...))；不再设置各通道输入队列、receive 异步生成器、多通道输入合并或统一输入读取任务。退出时停止通道后等待已提交请求及记忆任务，再关闭共享资源。本轮直接提交改造仅做静态检查，现有 QQ 测试入口已同步，未运行测试或真实连接验证。
